This note covers what was set up on your server, what went wrong along the way, and what still needs doing before anyone enters real patient data. I've tried to keep it readable — you shouldn't need to be a developer to follow most of it.

What we actually installed

The zip file (mjafi.zip.zip) had two things in it. First, the backend — that's the real application: database, login system, permissions, audit trail, all the rules about which hospital can see which patients. Second, a single HTML file — the screen clinicians would use.

The backend is up and working. The web page is also live at https://mjafi.trecsa.in. But here's the catch: the page you see right now is still running on demo data baked into the file itself. It doesn't talk to the backend yet. So if you log in and browse around, you're looking at a prototype, not the live registry.

In short: the engine is running. The dashboard is installed but not plugged in. That's the main thing left to do.

How it fits together on the server

Your Trecsa server already runs CyberPanel with LiteSpeed handling all websites. We couldn't use the Caddy setup that came in the zip because LiteSpeed already owns ports 80 and 443. So the layout ended up like this:

Browser → mjafi.trecsa.in (HTTPS) ↓ LiteSpeed (your existing web server) ├── / → the HTML page (public_html) └── /api/ → backend on 127.0.0.1:8010 (internal only) ↓ PostgreSQL database (internal only)

The database and API aren't reachable from the internet directly — only through LiteSpeed. That's intentional.

Problems we ran into

Nothing unusual for this kind of deploy, but worth recording:

Admin SSH login failed

The admin account rejected the password. Switched to root and that worked fine.

No Docker on the server

The backend is designed to run in Docker containers. Had to install Docker Engine from scratch — took a few minutes, one-time thing.

Port 80/443 already taken

The zip assumes Caddy will be your front door. On your server, LiteSpeed already does that job for every domain. We dropped Caddy from the setup and let LiteSpeed handle TLS and proxying instead. Same result, different path.

Config file formatting

One setting (REQUIRE_2FA_FOR_ROLES) needed to be in JSON format in the .env file, not plain comma-separated text. Small fix, but it blocked the first startup attempt.

Database app-user password

This was the annoying one. The database creates a separate low-privilege user (wm_app) for the API to connect as — that's what makes row-level security work. But the compose file wasn't passing the app password to the database container on first boot, so the user got created with the wrong credentials. Fix: add the password to the db service config, wipe the volume, start fresh. Migrations and seed ran cleanly after that.

"Site not visible"

From the server side, the site responds fine — we get HTTP 200, SSL is valid, DNS points to the right IP. If you still can't see it, it's usually one of these:

  • DNS hasn't propagated to your network yet (can take a few hours)
  • Browser cache — try a hard refresh or incognito window
  • You're on www and something's off with the alias (try without www)
  • The demo login screen looks blank until you click one of the user accounts on the left — the Sign In button stays greyed out until you do
  • Office firewall blocking the IP

Putting this on a main domain (shared hosting question)

People often ask: can we just upload this to regular shared hosting like any WordPress site?

Honestly — not really, not the full thing.

The web page (the HTML file) can go anywhere. Upload it, done. But the backend needs PostgreSQL (most shared hosts only offer MySQL), a always-on Python process, and ideally Docker. Most cPanel-style plans don't give you that.

Your realistic options:

  • What we did — VPS or dedicated server (your Trecsa box). Full control. This is what the software was built for.
  • Split setup — HTML on shared hosting pointing at an API hosted elsewhere. Works, but someone has to maintain two pieces.
  • Cloud VM — AWS, DigitalOcean, etc. Same idea as the VPS route, just rented differently.

If you want this on something like registry.yourhospital.in instead of a subdomain, the steps are the same — point DNS to the server, create the site in CyberPanel, upload the HTML, run the Docker stack, set up the proxy. The subdomain vs main domain part doesn't change much technically.

Security — what's in place and what isn't

The backend was clearly built with clinical data in mind. Centre isolation is enforced twice (in the application code and again at the database level), passwords use Argon2 hashing, there's login lockout after five failures, 2FA for senior roles, an audit log that can't be tampered with, and the API docs are turned off in production.

What's not sorted yet:

  • The demo frontend bypasses all of that — it's offline fake data
  • Test passwords are still the default for every account
  • Server firewall isn't locked down (everything's open on INPUT)
  • SSH is password-based — keys would be better
  • This server runs a lot of other things (mail, FTP, GitLab, WhatsApp hooks) on the same box
Before real patient data goes in: connect the frontend to the API, change all passwords, harden the server, test a backup restore, and make sure ethics approvals and data-sharing agreements are signed.

If something breaks — quick checks for your IT person

SSH in and run:

cd /opt/mjafi/wm-registry-backend
docker compose -f docker-compose.prod.yml ps
curl -s http://127.0.0.1:8010/health

You want to see both containers "Up" and the health response saying "status":"ok".

To restart the API after a config change:

cd /opt/mjafi/wm-registry-backend
docker compose -f docker-compose.prod.yml restart api

Backups run nightly at 2 AM to /opt/mjafi/wm-registry-backend/backups/. Log at /var/log/mjafi-backup.log. Nobody's tested a restore yet — worth doing once.
