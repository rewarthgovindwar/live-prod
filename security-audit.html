IMAGe WM Registry — Security & Code Audit

mjafi.trecsa.in  ·  18 August 2026  ·  Scope: backend (wm-registry-backend) + frontend HTML from mjafi.zip.zip

Related: Installation guide  ·  Registry (demo UI)

This report covers vulnerabilities and functional bugs found by reviewing the source code in the zip package and the live deployment at mjafi.trecsa.in. It is meant for developers and project leads — not as a formal penetration-test certificate.

Summary

The backend is well thought out for a multicentric clinical registry: centre isolation, role permissions, workflow states, audit logging, strong password hashing, and 79 automated tests including database row-level security checks. That said, there are gaps that must be closed before real patient data goes in.

Critical findings

Critical C1 — Website not connected to the backend

Where: IMAGe_WM_Registry_140826_1346h.html

The page at mjafi.trecsa.in looks like a full registry, but it runs entirely on sample data stored inside the HTML file. It never calls the live API, never checks passwords against the server, and never enforces centre isolation or audit rules.

Impact: All backend security is inactive for anyone using the website.

Fix: Connect login, patient records, imports, exports, and analytics to /api/v1/* with proper token handling.

Critical C2 — Database allows national role to read all records

Where: Alembic migration 0001_initial.py, policy patients_read

When the national coordinator session is active (app.national = on), PostgreSQL row-level security permits reading every patient row — including drafts and submitted records that have not been released to the pool.

The application code filters to verified/approved records via scoped_patients(), but the database itself does not. Any future endpoint that forgets that filter, or any direct query under the app database role, could expose pre-release records and hospital CR numbers from all centres.

Fix: Add a status condition to the national read policy (e.g. only VERIFIED and APPROVED).

High findings

High H1 — Metadata API is open without login

Where: /api/v1/meta/dictionary, /meta/roles, /meta/config

Anyone on the internet can fetch the full field dictionary, permission matrix, workflow transitions, token lifetimes, and import limits — no authentication required.

Fix: Require a valid login token for these endpoints, or strip sensitive detail from the public response.

High H2 — User table has no centre scoping at database level

Where: RLS policy users_all … USING (true)

Every authenticated database session can read all user accounts (emails, names, roles) if any code path runs a broad SELECT on the users table without an application filter.

Fix: Scope user-table RLS by centre, with a controlled exception for the national role.

High H3 — Locked accounts reveal themselves on login

Where: app/api/auth.py login handler

Wrong password returns a generic “invalid email, password or code” message. A locked account returns a distinct HTTP 423 with text explaining the lockout — which tells an attacker that the email address is registered.

Fix: Return the same generic failure message for locked and wrong-password cases.

High H4 — Defects in the shipped zip package

These are bugs in the package itself, not deployment mistakes:

  • docker-compose.yml does not pass POSTGRES_APP_PASSWORD to the database container, so the wm_app role is created with wrong credentials on first install.
  • .env.example shows comma-separated lists, but the application expects JSON arrays — startup fails unless the format is corrected manually.

Medium findings

Medium M1 — Query list loads all patients for lookup

Where: app/api/admin.py, list_queries

When building the query list, the code loads every patient row into memory to attach registry IDs. Combined with the national RLS gap, this can expose linkage to unreleased records.

Medium M2 — Import preview stores full file in database

Where: app/api/imports.py

The entire uploaded worksheet is stored in a JSON column between preview and commit. Patient identifiers sit duplicated at rest; uncommitted batches may linger.

Medium M3 — 2FA enrolment returns secret in API response

Where: POST /api/v1/auth/2fa/enrol

The TOTP secret is returned in plain JSON. Any intercept, log, or browser extension could capture it. Prefer QR-only delivery over HTTPS.

Medium M4 — TOTP secrets stored unencrypted in database

A backup compromise would allow 2FA bypass for Head of Department and national coordinator accounts. Column-level encryption is recommended.

Medium M5 — No rate limiting on auth endpoints

Per-account lockout exists after five failures, but there is no IP-level throttling. Distributed login attempts or refresh-token abuse are not blocked at the edge.

Medium M6 — Refresh tokens not tied to device

IP and user-agent are stored but not checked on refresh. A stolen refresh token works from another machine until it expires or is revoked.

Medium M7 — Parallel refresh race

Two simultaneous refresh requests with the same token could both succeed briefly before revocation is committed. Low probability, but could create duplicate valid sessions.

Medium M8 — Symmetric JWT signing (HS256)

A leaked SECRET_KEY allows forging any access token. Mitigated today by strong key generation and short token lifetime, but worth noting for key rotation policy.

Low & informational

  • L1 — /health exposes environment name (minor).
  • L2 — Patient list pagination total is wrong when filtering by IPSS risk or overdue follow-up in application code after the SQL query.
  • L3 — Audit log search allows % wildcards in the action filter (harmless but broad).
  • L4 — create_centre accepts a raw dict instead of a validated schema.
  • L5 — Demo frontend uses innerHTML with an esc() helper; fine for static demo data, must be rigorous when wired to live API fields.
  • L6 — Import size capped at 15 MB; reasonable but not a full denial-of-service strategy.

What the backend does well

Verified in source and tests — worth preserving:

  • Argon2id password hashing (64 MB, 3 passes)
  • Dummy hash verification on unknown emails (timing parity)
  • Refresh token rotation — old token dies after use (tested)
  • Centre scoping in application layer; foreign records return 404 not 403
  • Workflow state machine enforced server-side
  • Derived clinical values computed server-side; clients cannot submit them
  • Optimistic locking via version field
  • Append-only audit log; UPDATE/DELETE revoked on audit table
  • API documentation disabled in production mode
  • 79 automated tests including raw SQL RLS checks
  • Container runs as non-root user
  • Upload extension, size, and row limits on bulk import

Live deployment risks (mjafi.trecsa.in)

Separate from the zip code — current server state:

  • All seeded accounts still use temporary password ChangeMe#2026Registry
  • Shared server hosts mail, FTP, GitLab, and other sites alongside the registry
  • Host firewall not confirmed locked down
  • HSTS not set on the LiteSpeed vhost
  • Nightly backup scheduled; restore never tested

Recommended fix order

  1. Connect the frontend to the live API (C1)
  2. Fix national-role RLS to pooled-status-only (C2)
  3. Correct docker-compose.yml and .env.example (H4)
  4. Require authentication on /meta/* (H1)
  5. Tighten user-table RLS (H2)
  6. Unify login failure messages for lockout (H3)
  7. Add rate limiting on auth at LiteSpeed or application layer (M5)
  8. Replace seed accounts and force password change
  9. Encrypt TOTP secrets; stop returning secret in enrol response (M3/M4)
  10. Fix pagination total bug (B1)

Tests worth adding

  • National RLS: with app.national=on, draft patient rows must not be readable
  • /meta/dictionary without token → 401 (after fix)
  • Locked account login → same response body as wrong password
  • Parallel refresh with same token → only one succeeds
Bottom line: The backend is stronger than average for a registry prototype. The two blockers for production are the disconnected frontend and the database not enforcing the “pooled records only” rule for the national role. Fix those before any real clinical data.
